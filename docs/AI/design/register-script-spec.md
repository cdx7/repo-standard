# Spec — `register` (the deviations-register mapper)

*Draft, 2026-10-01, for tracker F17. It builds on a plan written in the first vendor-derived
repo to adopt the standard, and on the maintainer's decisions R1-R4 of 2026-09-30, plus Q1-Q5
of 2026-10-01 (§ 9). Built in four slices (§ 10) and released in 0.4.0. `history` (§ 2) was
added on 2026-10-15, with `track history`.*

- **What it is:** `bin/register`, a tool beside `bin/track` for a vendor-derived repo's
  register, `docs/official/DEVIATIONS.md`. It does for the register what `track` does for
  the tracker. The prose stays hand-written; the tool checks the structure and generates
  the summary views from it.
- **Decided (F17):**
  - **R1:** it lives in repo-standard;
  - **R2:** one header line per entry, carrying a `Source` field backed by a sources table;
  - **R3:** code and docs cite an entry as `register N`;
  - **R4:** it renders `DEVIATIONS.html` as well as the summary table.
- **Who uses it:** vendor-derived repos only. The first register it was built for had 37
  entries in 1,630 lines.
- **Dependencies:** the same as `track`: bash (>= 4, guarded at the door) + coreutils +
  `awk`/`sed` + `git` (for `map` and `history` only). No `jq`, no config file, no network.

---

## 1. The file it reads — `docs/official/DEVIATIONS.md`

The register stays a document a person reads in Okular or ReText. The tool relies on six
conventions and ignores everything else (the status line, the H1, intro prose, unnumbered
`## ` sections such as "repo-standard adoption").

**1. The types table** — hand-kept, under a `## Types` heading (Q1, decided 2026-10-01). It
replaces a hand-kept legend list, and each register declares its own types:

```markdown
## Types

| Type    | Meaning                                         |
| :------ | :---------------------------------------------- |
| pin     | a version we lock to                            |
| DG gap  | something the DG assumes or omits that we add   |
```

A type is any text without `·`, `|` or a line break, and is unique; the meaning is free
text.

**2. The sources table** — hand-kept, under a `## Sources` heading:

```markdown
## Sources

| Key    | Document                                  | Version | Date       | Path |
| :----- | :---------------------------------------- | :------ | :--------- | :--- |
| DG     | Production Environment Deployment Guide   | v1.9    | 2026-08-05 | ../reference/acme/2026-08/Acme_Deployment_Guide_v1.9.pdf |
| AppReg | App Registration Setup Guide              | v1.1    | 2026-08-10 | ../reference/acme/2026-08/Acme_App_Registration_Guide_v1.1.pdf |
```

Its two load-bearing columns:

- **Key:** a letter followed by letters, digits or hyphens; unique.
- **Path:** relative to the register's own folder, so the same link works in the Markdown
  and in `DEVIATIONS.html`, which sits beside it. The path is what tells two drops apart
  when they reuse file names.

**3. The summary block** — generated, between two markers. Nothing between them is edited
by hand:

```markdown
<!-- register:begin — generated by bin/register; edit nothing between the markers -->
| # | Deviation | Type | Status | Original | Updated | Source |
…
<!-- register:end -->
```

The Deviation column is the entry's heading title, as written (Q2, decided 2026-10-01): one
title per entry, nothing extra to keep in step.

**4. Entry headings** — `## N. Title`, where `N` is a positive whole number, unique, and in
ascending order down the file. A heading needs a blank line before it: without one, Okular
nests the heading inside the previous entry's last bullet (found in the first register).

**5. The header line** — the first paragraph under each entry heading, followed by a blank
line. It may wrap over several lines; a blank line ends it. The values below are made up, to
show every form:

```markdown
## 12. An example entry

*Type:* harness · *Status:* active · *Original:* 2026-05-12 · *Updated:* 2026-05-21,
2026-09-17 · *Source:* DG v1.9 § 3 p.6; AppReg v1.1 § 7 p.6

- **DG says (v1.9 § 3, p.6):** …
```

The rules for each field:

| Field | Rule |
| :-- | :-- |
| **Type** | One of the types in the types table. |
| **Status** | `active`, `moot` or `closed`. A closed entry stays in the file and keeps its number, as the tracker keeps done rows. |
| **Original** | One date, `YYYY-MM-DD`: when the deviation first landed. |
| **Updated** | Dates in ascending order, separated by `, `, or `—` for none. |
| **Source** | One or more `<key> <location>`, separated by `; `. The key must be in the sources table; the location is free text (version, section, page). Or `none` when no vendor document addresses the point. |

Fields come in that order, separated by ` · `, each label in `*…:*` form. Wrapped lines are
joined with a space before parsing.

**6. Fenced code blocks** are skipped by every parser, so an example quoted in the prose
never counts as an entry, a header or a source (`track`'s B84 lesson).

## 2. Commands

### `register render`
- Reads the register and writes two things:
  - the summary block, rewritten in place between the markers;
  - `DEVIATIONS.html`, beside the register (§ 3).
- Output is deterministic: no timestamps, fixed order. So `--check` can byte-compare.
- **Refuses before writing anything** when the register fails validation (§ 2, `check`):
  it never generates a table from a header it could not parse.

### `register check`
- **Validates** the register:
  - every entry has a header line, with all five fields valid (§ 1.5);
  - a blank line follows each header and precedes each `## ` heading;
  - entry numbers are unique and ascending;
  - every type and source key used is defined, types and keys are unique, and every
    defined path exists;
  - exactly one marker pair exists, in order.
- **Checks staleness:** renders to a temp and compares with the summary block and
  `DEVIATIONS.html`, leaving out the page's citation block (Q5). Stale output exits 1 with a
  `STALE` token, the way `track render --check` does, so the pre-commit hook can tell
  staleness from invalid input.
- Prints each problem with its line number; exits 0 only when everything holds.

### `register map [--entry N | --file PATH] [--all] [--check]`
- **Scans** the repo's tracked files (`git ls-files`) for citations: `register N`, with `N`
  a whole number.
- **Default scope** (Q3, decided 2026-10-01): the files that describe the build as it is
  now. It leaves out the register, the generated pages (`DEVIATIONS.html`, `tracker.html`,
  which repeats `tracker.md`), `docs/reference/`, the dated records in `docs/AI/` and the
  retired files in `z-deprecated/`. Dated records keep citing entries that have since closed;
  in the first register's repo they held 194 citations in 52 files against 46 in the live
  files, and would bury the live warnings.
- **`--all`** drops the exclusions for one run ("where has entry N ever been cited?") and
  changes nothing.
- **Prints** each entry with the files (and lines) that cite it, and each file with the
  entries it cites. `--entry` and `--file` narrow the listing.
- **Flags:**
  - a citation of a number with no entry (an **error**);
  - a citation of a `closed` entry (a **warning**);
  - an entry no file cites (**listed**, not a problem: harness-only entries are legitimate);
  - items in `DEVIATIONS applied` comment blocks that carry no `register N`, **listed for
    triage**. The tool never guesses a number for them.
- `--check` exits 1 only on errors. `verify` runs it (§ 5); the pre-commit hook does not,
  because a citation lives in any file and the hook stays fast.

### `register history <N>`
- **Read-only:** prints entry N's history from git, oldest first in each part. No write, no
  lock, no render; nothing is recorded (decided 2026-10-15, with `track history`). It needs
  no markers, since a register's history predates them.
- **Versions of the entry:** every commit that touched the register, followed across renames.
  In each version, the entry's section, from `## N. ` to the next `# ` or `## ` heading and
  fence-aware, is compared with the previous version's. A version is listed where it changed,
  naming each change: `text changed (a → b lines)`, `title → "…"`, `header added: <fields>`,
  each header field that changed (`Status active → closed`, `Updated — → 2026-10-15`, …),
  `header removed`, `entry removed`, `entry back`. Line endings alone make no version.
- **The first version** is the first commit with a `## N. ` heading. When no earlier version
  of the file had any numbered heading, that commit numbered entries written before it, and
  the line says the entry may be older.
- **Uncommitted:** when the working copy's section differs from the last commit's, a last
  line marked `uncommitted`, with no date.
- **Commits that name it:** messages in HEAD's history that name the entry in one of five
  forms, in any case: `register N`, `register entry N`, `register entries N`, `DEVIATIONS § N`
  and `DEVIATIONS #N` (`DEVIATIONS.md` too). Each is matched whole, as `map` matches: not
  inside a longer number, and not where `N` runs on into a date or a version; in a list such
  as `register 20/22`, only the first number counts. A message is read with its lines joined,
  since a wrapped message often splits a citation in two (`git log --grep` matches one line
  at a time). Not matched: a bare `§ N` or `entry N`, which usually mean something else.
- **Cited in:** the files and lines that `register map --entry N --all` lists.
- **Exit:** 0 when the entry has any history, an entry whose heading is gone included (headed
  "no longer in the register: last seen in <hash>, <date>"). 1 for a number never in the
  file, one that is not a whole number from 1 (a leading zero is ignored), or a register
  outside a git work tree. A shallow clone prints the history it has and says it is
  incomplete.

```
$ register history 12
12  An example entry   (harness, active)

Versions of the entry (3)
  2026-05-12  5d1e0b4  first appears as entry 12
  2026-05-21  a07c3f9  text changed (14 → 19 lines)
  2026-09-17  e2b8d61  header added: harness · active · 2026-05-12 · 2026-05-21 · DG v1.9 § 3 p.6

Commits that name register 12 (1)
  2026-05-21  a07c3f9  fix: the harness waits for the second profile (register 12)

Cited in 1 file   (as register map --entry 12 --all)
  scripts/harness.sh: 4, 88
```

## 3. `DEVIATIONS.html`

- The same kind of self-contained page as `tracker.html`: one file, no network, opened in a
  browser.
- **Contents:** a row per entry (number, title, type, status, dates, sources) that expands to
  show which files cite it.
- **Filters:** chips for type, status and source key; a search over number, title and the
  citing files.
- **Links:** each source key links to its document by the relative path.
- **Built from `bin/track`'s page shell, copied into `bin/register`** rather than shared. A
  shared library would be a new machinery file in every repo, and the two pages will
  diverge anyway. The cost is two copies of similar styling.
- The page does **not** carry the entries' prose; the Markdown stays the place to read it.

## 4. Behaviour and guardrails

- **Finding the register:** `$REGISTER_FILE` if set; else the repo the invoked copy lives in
  (`$0/../docs/official/DEVIATIONS.md`), as `track` does; else the git toplevel's
  `docs/official/DEVIATIONS.md`. Whatever resolves must contain a `<!-- register:begin` marker
  outside a fenced block, or every command refuses before writing.
- **Opt-in by markers:** a register without the marker pair is treated as not yet migrated.
  `check` and the pre-commit hook say so and pass; `verify` warns. This lets `sync` deliver
  the tool before a repo's register has its headers (§ 6).
- **Atomic writes:** temp file, then `mv`; a `DEVIATIONS.md.lock` directory serializes
  writers. Only the summary block is rewritten; every byte outside it is kept.
- **Refuses a raw `0x1f` byte** in the register, as `track` does (its field separator).
- **No commits.** It edits the working tree; committing stays the maintainer's call.

## 5. How the standard carries it

- **`template/bin/register`**, the first machinery file only vendor-derived repos get:
  - `init --vendor-derived` installs it; `init --authored` does not.
  - `sync` installs and updates it only when the stamp says `(vendor-derived)`. A
    vendor-derived repo's healthy sync then reads `7 unchanged`, not 6, and STANDARD.md
    says so.
  - `verify`, in a vendor-derived repo, checks that it is present and executable. It runs
    `register check` (a failure when stale, like the tracker check; a warning when
    invalid) and `register map --check` (a warning on dangling citations). In an authored
    repo, a `bin/register` gets a mismatch warning, like the other vendor-derived slots.
- **`.githooks/pre-commit`** (shared by every repo) gains a second block. It mirrors the
  tracker block:
  - it acts only when `docs/official/DEVIATIONS.md` is staged;
  - it checks the **staged** register and staged `DEVIATIONS.html`, not the worktree;
  - it prints absolute fix commands;
  - it lets the commit through with a message when `bin/register` is missing;
  - in an authored repo nothing stages a register, so the block never runs.
- **`init`'s register skeleton** changes from today's single table to the entry form: the
  status line, the H1, empty types and sources tables, the marker pair and no entries.
- **Docs in the same release:**
  - STANDARD.md (the archetype slot, a `register` section, the sync count);
  - the transfer prompt;
  - README;
  - CHANGELOG.
- **The source tree** (repo-standard is not vendor-derived) carries no `bin/register` of its
  own. Tests run against fixtures (§ 7).

## 6. Taking it up in a repo with an existing register

In a vendor-derived repo whose register predates the tool, in this order, each step on its
own go:

1. `bin/sync`: delivers `bin/register` and the new hook. The register has no markers yet, so
   nothing blocks. `sync` does not manage `.gitattributes`: in a repo adopted before 0.4.0,
   add `bin/register text eol=lf` beside its `bin/track` line by hand.
2. One commit:
   - the types table (from any legend the register kept) and the sources table;
   - a header line for every entry, written from the old summary table and the entries;
   - a blank line before every entry heading;
   - the old table replaced by the marker block, generated by `register render`, plus
     `DEVIATIONS.html`;
   - any disagreement between the old table and an entry listed for the maintainer, not
     settled silently;
   - where the old table's summary says it better than the heading, the wording moved into
     the heading, each case listed for the maintainer.
   - A location that itself contains `; ` (such as `§ 19; was § 18`) needs `, ` instead,
     since `; ` separates Source items.
3. One commit: every citation rewritten to `register N`. The unnumbered "DEVIATIONS applied"
   items are triaged by hand.
4. From then on, register amendments are made with the tool in place.

## 7. Tests

The repo keeps no committed test suite. Each release has been checked by a **flip suite**
in the session scratchpad: the previous release's tools against the worktree, where every
reproduction flips and every control holds. `bin/register` follows the same pattern, with
at least these cases:

- **Fixture registers:**
  - a valid one;
  - each validation failure of § 2 alone (missing header, no blank line after it, unknown
    type, unknown source key, missing path, duplicate number, out-of-order number, two
    marker pairs);
  - a fenced example entry;
  - a raw `0x1f`;
  - a register without markers.
- **Render:**
  - idempotent (render twice, byte-identical);
  - bytes outside the markers unchanged;
  - `check` passes right after `render`, and fails with `STALE` after a hand edit to a
    header.
- **Map:** citations of an existing, a missing and a closed entry; an uncited entry; a
  "DEVIATIONS applied" block with and without numbers; a citation in each excluded area
  (absent by default, present with `--all`).
- **Integration:**
  - `init --vendor-derived` installs the tool and `--authored` does not;
  - `sync` on each archetype (7 vs 6 unchanged);
  - the pre-commit hook on a staged stale pair;
  - `verify` on both archetypes.
- **Viewers:** the generated table and a fixture register through Okular's discount and
  ReText's markups, as on 2026-09-30.
- **A real register:** a scratch copy of the first register, converted, renders and checks
  clean, and its summary matches its old table entry by entry, apart from listed
  differences.

## 8. Not doing

| Not doing | Why |
| :-- | :-- |
| Writing or rewriting entry prose | The prose is the register's judgment; the tool keeps only the structure. |
| Deciding whether a deviation still holds | That is a re-read against the vendor documents, not a parse. |
| Renumbering, merging or deleting entries | Numbers are cited from code; a closed entry keeps its number. |
| Guessing numbers for unnumbered citations | Listed for triage; which entry an item belongs to is a judgment. |
| A config file | Types and sources live in the register itself. |

## 9. Questions settled while drafting (all decided 2026-10-01)

- **Q1. Where the types come from. Decided 2026-10-01 (the maintainer: "Yes"):** a
  hand-kept `## Types` table in the register (§ 1.1). The first register's five types (pin,
  DG gap, harness, scripted, DG bug) are its own; another vendor's register would need others.
- **Q2. The summary's "Deviation" column. Decided 2026-10-01 (the maintainer: "Yes"):**
  generated from the entry heading (§ 1.3). The first register's table summaries (42 to 233
  characters) differed from its headings; the better wording moves into the heading at the
  conversion.
- **Q3. The map's default scope. Decided 2026-10-01 (the maintainer: "Yes"):** the live
  files only, with `--all` for a one-off full sweep (§ 2, `register map`).
- **Q4. The version number. Decided 2026-10-01 (the maintainer: "Yes"):** 0.4.0. Like
  `verify` (0.2.0) and `sync` (0.3.0), it is a new tool that `sync` copies into repos, and it
  changes the shared hook and `init`'s skeleton. `sync` compares versions with `sort -V`, so
  0.4.0 orders after 0.3.27.
- **Q5. The page's citations and staleness. Decided 2026-10-01 (the maintainer: "go, build
  slice 2 that way"):** `render` writes the citing files into `DEVIATIONS.html`, between two
  marker lines, and `check` (with the hook) leaves those lines out of its comparison.
  `map --check` warns when they no longer match the live files.
  - **Why:** the citations come from every live file, not the register. Compared strictly,
    a commit that only moves a citation would leave the page stale where the hook, which acts
    only when the register is staged, cannot see it.
  - **Not chosen:** citations only in `map`'s output (drops what R4 promised), and a separate
    citations file (one more generated file in every vendor-derived repo).

## 10. Built so far

**Slice 1, 2026-10-01: `check` and `render`,** in `template/bin/register`. It follows §§ 1–4,
plus these rules that those sections leave open:

- **Entry headings:** `N` has no leading zero and at most 9 digits. A `## ` heading that
  starts with a digit but is not `## N. Title` is an error, so a typo cannot drop an entry
  without a word.
- **Header lines:**
  - the header ends at a blank line. A line inside it that starts a new block (a list item,
    heading, quote, table row, fence, HTML, or a `---`, `===`, `***` or `___` line) is an
    error;
  - in Source, `none` must stand alone;
  - not detected: a paragraph glued onto a header whose Source lists documents. It reads as
    part of the last location.
- **Tables:** the header rows must read `| Type | Meaning |` and
  `| Key | Document | Version | Date | Path |`. An absolute Path is refused.
- **Output:**
  - `check` prints every problem as `file:line: message`, sorted by line;
  - `render` leaves a file it would not change untouched;
  - a CRLF register gets CRLF lines in its summary block.
- **`DEVIATIONS.html`:** an entry's detail shows its type's meaning, its dates, each source
  with a link, and `register N`. The citing files, and searching by them, come with `map`
  (slice 2).

**Slice 2, 2026-10-01: `map`,** and the page's citations (Q5):

- **A citation** is `register N` in any case, read from the worktree copy of a tracked file
  (binary files skipped), counted once per number per line. It does not match inside a
  longer word (`preregister 3`), or when `N` runs on into a date or a version
  (`register 2026-09-30`, `register 1.36`). Not detected: a citation wrapped across two lines,
  and every number after the first in `register 17, 21`.
- **A "DEVIATIONS applied" block** opens on a comment line naming it and runs to an empty
  comment line, the first line that is not a comment, or a line back at the header's own
  indent once bullets have begun.
  - Its items are its bullets, with their continuation lines. A deeper line that starts
    with `-`, `*` or `+` continues the item above it.
  - With no bullets, the text after the colon is the one item; `none` means no items.
- **Narrowing:** `--file` scans the named file even inside an excluded area, given from
  the current directory or from the repo root; it must be tracked. `--entry` with `--check`
  checks only that entry.
- **The page:** an entry's detail lists the files and lines that cite it, labelled as of the
  last render, and the search covers those paths. A banner lists citations of entries that
  do not exist.
- **Outside a git work tree:** `map` refuses; `render` writes the page without citations and
  says so.

**Slice 3, 2026-10-01: the integration** (spec § 5):

- **`REGISTER_BASE`:** when set, Source paths resolve against it instead of the register's
  folder. The hook sets it to the worktree's `docs/official/` while it checks the staged copy
  from a temp dir.
- **`init --vendor-derived`:**
  - installs `bin/register` and writes the entry-form skeleton (an intro naming the header
    form, empty Types and Sources tables, the marker pair);
  - renders `DEVIATIONS.html` when absent, as it does `tracker.html`;
  - pins `bin/register text eol=lf` and ignores the tool's temp files, through the two
    skeletons; a `.gitignore` the repo already has gains whichever of the two temp-file
    rules it lacks (B152).
- **`sync`:**
  - carries `bin/register` only when the stamp says `(vendor-derived)` (`unknown` and
    both-archetype stamps get none);
  - under the same test, adds whichever of the tool's two temp-file ignore rules the repo's
    `.gitignore` lacks (B152);
  - does not re-render the register, since its summary block sits inside the authored file.
    When the tool's output would change, it prints a NOTE with the command, counted as no
    drift.
- **`verify`:**
  - in a vendor-derived repo: the tool's presence, exec bit and committed mode;
  - `check`: stale is a FAIL, like a stale tracker (decided 2026-10-01); not migrated and
    invalid warn, each with its own remedy;
  - `map --check` (a missing entry, or the page's citations behind the files, warns);
  - in an authored repo, a `bin/register` is an archetype mismatch.
- **The hook:** the second block checks the staged register and page. A missing `bin/track`
  now skips only the tracker block, not the whole hook.
- **On adoption:** a vendor-derived repo's `verify` gains two warnings (the tool missing, the
  register not yet migrated) until steps 1 and 2 of § 6 are done.
